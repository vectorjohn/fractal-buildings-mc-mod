Inside the City Planner

How the mod gets from a world seed to a metropolis and the roads around it, where it asks Minecraft for terrain on the way, and why a cold arrival takes about 70 seconds where vanilla takes 4. The animated timeline uses real planner output for one city: metropolis s2_m6 on seed 987654321, the same city every performance row measures.

Column read

One block column: floor height and water depth from vanilla's noise (getBaseColumn through SparseColumns). About 0.35 to 0.55 ms each. Used on sparse lattices: region cells every 64 blocks, the skeleton every 32, road stations every 8.

Chunk fill

All 256 columns of a 16 x 16 chunk at once (ColumnMemo + ChunkFill.WINDOWED). About 1.9 ms, so one column read costs about a quarter of a chunk. Used where reads are dense: the junction field, the quay trace, district plans.

Nothing exists yet

Planning runs before the chunks exist, so it can't read generated blocks. Every answer is a pure function of (seed, position): chunks can generate in any order, and nothing we read is reused by vanilla later.

Read costs: docs/review/regionperf-decision.md section 4 ("Two ways we read terrain"); A1 log docs/log/2026-10-22-p6-a1-probes.md (1.9 ms windowed fill against 141.6 ms for 256 single columns, measured under load, so ratios only); SPARSEREADS note in docs/NOTES.md.

2 · Architecture

Which code does each phase, and on which thread

Two halves. planner-core is pure Java and never sees Minecraft: it reads terrain only through probe interfaces. mod supplies the live probes (vanilla noise), runs the planner from Minecraft's structure system and its own worker pools, and writes the blocks. The CLI and the viewer use the same planner over recorded terrain, which is why every picture on this page could be made outside the game.

Why the first chunk waits ~39 s

A structure start for a tile can't place its pieces until its settlement's shared work exists: the street network, the junction field and the quay runs near it. In a cold world nothing has computed them, so one vanilla worker computes them inside the start. The other 80 chunks of the block cost 1.6x vanilla (39 against 24 ms median).

regionperf section 6 (COLDCHUNK: what the cold chunk is doing), PERFBASE table.

Why the server freezes

The server thread itself runs none of our planning. It freezes because vanilla code on it (spawning, the player's own chunk) asks for a chunk whose structure start is still waiting. On cold arrival the longest tick is 8.5 to 9.5 s against 78 to 96 ms in vanilla. An earlier local profile caught a 104 s freeze on an elytra flight into this city (busy host, not a valid timing; the mechanism is structural).

PERFBASE table; docs/review/profile-metropolis.md "What the player actually feels".

95 % of it is vanilla's noise

Of the CPU on the cold block, our own code is 2 to 3 %. The rest is vanilla's terrain noise that our probes ask for (GradientNoise.permute, aquifers, density functions). So the levers are fewer chunk fills, more threads, or doing the work earlier; making our own code faster barely moves the total.

4 · What we tried

Why reading fewer columns doesn't help

The tempting idea: read half the columns (a checkerboard) and interpolate. It fails because cost is per chunk filled, not per column. A chunk fill costs about the same as 4 to 5 single columns, and the busy consumers already touch 14 to 17 columns in every chunk they touch. Thinning skips no chunks. On a line (a street) it is worse: an unread column is interpolated from its four neighbours, and two of those lie off the street, so the checkerboard reads more columns, in more chunks. Try it.
