# S3 Multi-start city

## Question

Can 2-4 starts (one per district of a region cell) share one lazily built, cached city plan and join seamlessly? Evidence asked for: block hashes per chunk identical whatever order chunks generate in; no seams at district or chunk borders. Gate extras: a road that crosses a district border, and `/locate` finding the city through a `RandomSpreadStructurePlacement` subclass.

## Result

**Yes, with one correction to the evidence criterion.** The design works as written: a custom `Structure` + a `RandomSpreadStructurePlacement` subclass + a plan built once per cell in the piece builder. Every block the city writes is identical in all 7 generation orders, no block is written twice, and the road network is one connected component across all district borders. But a **whole-chunk** hash is *not* order-independent in vanilla itself (about 80-99 % of chunks differ between two orders with no mod involved), so the usable criterion is "blocks owned by our pieces", which is exact.

## What was built (throwaway, branch `claude/spike-s3`, `mod/src/main/java/dev/fractalbuildings/spike3/`)

- `CityGrid` (pure): district = 12x12 chunks (192 blocks), cell = 2x2 districts, 50 % of cells are cities (hash of seed, cell). Start chunk = district centre chunk, so a box stays within 6 chunks of its start.
- `S3Placement extends RandomSpreadStructurePlacement`: overrides `getPotentialStructureChunk` (district centre chunk, for `/locate`) and `isPlacementChunk` (= `CityGrid.isDistrictOrigin(seed, x, z)`). Own registered codec; JSON `structure_set` with `"type": "fractalbuildings:s3_districts"`.
- `S3Structure`: `findGenerationPoint` re-checks `isDistrictOrigin` (because `StructureCheck` for `/locate` never consults the placement), samples one height, and returns a stub whose lazy lambda calls `CityPlan.get(seed, cell)` and adds this district's pieces.
- `CityPlan` (pure, 2D): global road rect list (an E-W road straddling the inner district border, a N-S road with a jog) plus per-district buildings from a per-district sub-seed (`hash(seed, districtX, districtZ, purpose)`). Cached in a `ConcurrentHashMap.computeIfAbsent`. About 125 buildings per 2x2 city.
- `S3Piece`: one piece per building, one road piece per district. Saves only (cell, district, kind, index, baseY); `postProcess` regenerates its blocks from the cached plan, clipped to `chunkBB` and, for roads, to the district box. The `random` argument is unused.
- City-wide base height is sampled once at the cell centre by every start (a pure noise call), so all districts agree.

## Evidence

Test: `S3CityRun` + `S3ClientGameTest` (`mod/src/gametest/...`), driver `spike-s3-run.sh <outdir> [orders]`. Fixed seed 424242, normal overworld, structures on, one fresh singleplayer world per order inside one client launch. Cell (0,0): 24x24 = 576 chunks, 4 starts, 125 buildings, 220,211 planned blocks (90,959 solid). Orders: `forward`, `reverse`, `shuffle1`, `shuffle2`, `spiral` (centre out), `threads1` (8 threads requesting shuffled chunks), `threads2+evict` (same, plus a thread clearing the plan cache every 2 ms: 488 rebuilds during generation, 2391 evictions).

**Why a client test:** the server game-test world (`GameTestServer`) is flat, seed 0 and `generate_structures=false`, so no structure ever generates there.

Per-chunk hashes compared with `forward` (final code, structure step `top_layer_modification`), number of chunks that differ out of 576:

| Order | whole chunk | masked (vegetation as air) | **solid plan blocks, in world** | plan air blocks, in world | **what our pieces wrote** |
|---|---|---|---|---|---|
| reverse | 575 | 571 | **0** | 17 | **0** |
| shuffle1 | 529 | 509 | **0** | 5 | **0** |
| shuffle2 | 537 | 522 | **0** | 8 | **0** |
| spiral | 455 | 450 | **0** | 10 | **0** |
| threads1 | 513 | 494 | **0** | 6 | **0** |
| threads2 + evict | 518 | 497 | **0** | 8 | **0** |

- "What our pieces wrote" is a ledger hook in `postProcess` (position, block id per write). Identical in all orders, so the piece output is a pure function of seed + position.
- **Vanilla baseline (answers the "vanilla village baseline" probe):** the whole-chunk hash differs for 455-575 chunks between two *different* orders and for 218-238 chunks between two runs of the *same* order (thread timing alone). Dumping three chunks showed the differences at chunk edges: short grass, moss carpet, clay and diorite blobs, deepslate/clay swaps (features that overlap neighbouring chunks). Masking vegetation does not fix it. So the whole-chunk hash cannot be the test; never gate on it.
- **Reference check:** the world is compared with a raster built from the global plan (no districts, no chunks). 0 of 90,959 solid blocks differ. The ledger matches the plan exactly: 220,211 expected, 0 extra, 0 missing, 0 wrong value, **0 blocks written more than once**.
- **Seams:** 3,705 road tiles, 795 within one block of a district border, 0 wrong. The world's own road blocks form **1 connected component** (3,705 of 3,705 tiles). The E-W road straddles the district border (3 blocks one side, 2 the other), the hardest case.
- **Starts:** 4 of 4 exist; each reaches 6 chunks from its start chunk (limit 8); 25-36 pieces, 609-727 B gzip NBT per start (about 20 B per piece, references only). Each survives `createTag` then `loadStaticStart` (same piece count and box).
- **Plan cache:** 16 threads on one key build the plan once and share one instance. Plan hash after eviction and rebuild is byte-identical (`ae9d511c...`). Plan builds in 61-164 us warm (2-4.5 ms on the first, cold JIT call); one plan per cell, not per start.
- **`/locate`:** `findNearestMapStructure` from (0,0) returns a district origin at 135 blocks, the same distance as the brute-force nearest origin (a tie between two); from the city centre it returns a district of that city. Cost 0-4 ms. It returns the nearest *district start*, not the city centre.
- **Placement check:** `isDistrictOrigin` 3-36 ns per call (5 M calls, JIT warm-up included). It does no world access.
- **9 starts (cell 3x3 districts, 1,296 chunks):** same result: 0 differing solid/write chunks between `forward` and `threads1`, 526,788 blocks written once, 1 road component, 25-34 pieces per start.

### Vanilla trees growing into the city, and the structure step

With the default step `surface_structures`, features run **after** the structure, and dark oak trunks grew on a roof and a road, replacing 2-4 of 90,959 solid blocks in 3 of 5 orders run (reverse, shuffle1, threads1; `forward` and a second `forward` had none; the trunk's `dirt` base replaces our block). Our ledger was still exact; the *world* differed. Setting the structure's `step` to **`top_layer_modification`** (the last step, after vegetation) gave 0 solid mismatches in all 7 orders, and cut the air-volume intrusions from about 200 to 16-37 blocks. Remaining intrusions are leaves/vegetation in our air volumes. Adopt a late step unless S5 finds a reason not to.

### Mutation checks (each fails the test as intended)

| Change | Caught by |
|---|---|
| road district box one block too large (overlap) | ledger: 436 blocks written twice |
| road district box one block too small (gap) | ledger: 416 missing blocks; 104 solid mismatches; road network in 3 components |
| wall material from a shared counter (hidden global state) | ledger wrong-value 9,318; per-chunk write hash differs in 76 chunks between `forward` and `reverse` |

### Timings (rough, **not** S6 grade)

576 chunks took 4.7-18.6 s (8-32 ms per chunk) at load average 7-27 on a shared 20-CPU box (other agents running); 1,296 chunks took 38.7 s. The threaded orders were the fastest, but the load varied too much to conclude anything. Piece building is cheap here (2-3 plan builds per world: this cell plus, inferred, neighbour cells whose starts generation touched). Use S6 for real numbers.

## What it means for the design

1. **Adopt structure-based, one start per district, as in the synthesis.** Nothing in the pipeline fought it.
2. **Make the plan 2D and pure: (seed, cell) to layout.** Heights come from the per-start noise sample, not the plan. Rebuild after eviction is exact, so the cache can be a plain bounded LRU.
3. **Ownership by construction:** global feature (road) as one rect list, each district owns its box (a partition of the plane, boxes meet at block boundaries), each piece also clips to `chunkBB`. No cross-start coordination, nothing to order.
4. **The test criterion is the ledger (what pieces wrote) plus a reference raster from the global plan**, not a whole-chunk hash. Keep this test in Phase 4; the vanilla noise is the reason. Keep the mutation switches (`S3_MUTATE`) idea: three cheap mutants prove the test can fail.
5. **Structure step:** use `top_layer_modification` so vegetation cannot overwrite our blocks (to be confirmed with S5 beard behaviour; the beard is applied by the structure's `terrain_adaptation`, independent of the step).
6. **`/locate` works** through the `RandomSpread` subclass; `findGenerationPoint` must repeat the origin test because `StructureCheck` ignores the placement. `/locate` points at a district, not the city centre (`locate_offset` is clamped to 16 blocks). A city-centre target needs a different mechanism (explorer map, own command).
7. **Gaps to handle in the real design:**
   - *A rejected district leaves a hole.* Per-start `isValidBiome` is checked at the stub position; one ocean district drops its start and cuts the road. Decide suitability per city/cell from the region layer (pure), use a broad biome tag, and never let one start fail alone.
   - *A start is created only when its chunk generates.* Adding the mod to an old world gives no districts in already-generated chunks.
   - *Vanilla structures overlap cities* (the cell referenced a ruined portal, ocean ruin and six mineshafts). S8's veto handles surface ones.
   - *Not tested here:* roads across a **cell** border (both cells would need a shared crossing point from a hash of the edge, which is straightforward but unproven), terrain adaptation (S5), a real save/reload from disk (only the NBT round trip), and large piece counts (S6).

## Limits on district count and plan size (John wants unbounded cities)

- **Number of districts is not limited** by the pipeline: placement is O(1) per chunk with no state, each district is independent, `/locate` is pure.
- **District size is limited to about 16 chunks** (a start reaches 8 chunks; +12 blocks with `terrain_adaptation`, so use at most about 14). We used 12 (192 blocks).
- **One start per `Structure` type per chunk.** Any second layer over the same area (walls, rings) needs its own `Structure` type.
- **A city is bounded by the plan cell:** the plan is built whole per cell and cached, so memory is cells x (roads + lots). A 3x3-district cell was 268 buildings and a 2 ms cold build; fine up to a few thousand lots. For cities bigger than one cell, adjacent cell plans must agree on border crossings.
- **Per-start cost grows with its piece count:** `placeInChunk` tests every piece's box for each chunk (O(pieces) per chunk), the start is saved with all pieces (about 20 B each as references), and starts are created on the single serial worldgen lane. S6 measures the large end.
- **The structure box is the union of its pieces**; every chunk within 8 of a start records a reference, so a bigger district means more references per chunk.

## How to re-implement the test properly

- Keep the shape: one client game test (`setUseConsistentSettings(false)`, fixed seed) that makes one fresh world per order and runs `runOnServer`. Server game tests cannot generate structures.
- Add the ledger hook behind a test flag (a static map in the piece, default off) rather than a global; hash (position, block id) per chunk sorted by position.
- Orders: forward, reverse, two shuffles, spiral, 8-thread shuffled `getChunkFuture(...).join()` with `server.managedBlock` on the main thread, and an evictor thread. Compare per-chunk hash files across worlds in one launch.
- Reference raster from the *global* plan; compare solid blocks only (vanilla features may touch air); fail on ledger mismatch, treat world-vs-raster mismatch above 0.1 % of solid blocks as the failure.
- Put the hash comparison into the Phase 4 determinism layer, and keep the three mutants as test-the-test cases.
