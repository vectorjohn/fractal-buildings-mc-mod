# S9: procedural `StructurePoolElement` inside vanilla villages

## Question

Can a custom pool element put generated houses into vanilla villages (footprint
fixed per element, content regenerated at `place` from seed and position), with
identical blocks whatever the chunk order? Also: does Lithostitched change that?

## Answer

**Yes.** Verified on 26.3 / Fabric API 0.162.0 in a server game test.

- 3 plains villages (start chunks (300,300), (340,300), (300,340)): 13, 15 and 9
  of our houses (of 142/125/82 pieces); 1790, 1956 and 1143 of our blocks.
- Per-chunk hashes of the blocks inside our pieces' boxes were **identical**
  for ascending, reversed and shuffled chunk order, with a different
  decoration `RandomSource` for the shuffled run, and for a start saved to NBT
  and reloaded. Every house has a junction (is wired into the street graph).
- Mutation check: mixing the supplied `random` into the content seed fails the
  test.

## What was built (throwaway; `mod/src/gametest/.../s9/`)

- `ProceduralHouseElement` (`fractalbuildings:procedural_house`): codec
  `{width, depth, projection}`. Box is `width x 8 x depth`, fixed per element;
  one jigsaw `minecraft:building_entrance` (name = target) at local
  `(w/2, 1, 0)`, facing north, ROLLABLE, rigid. Everything is rotated about the
  origin with `StructureTemplate.transform`, like a template, so
  `getBoundingBox`/jigsaw/`place` agree for all 4 rotations.
- `place`: content seed = hash(world seed, piece position, rotation, w, d);
  **the passed `random` is ignored**. Picks wall/roof material, wall height 3-4,
  windows, gable ridge along the long axis; writes only inside `chunkBB`; sets
  flag 2.
- Registered in a `ModInitializer` of the test mod
  (`Registry.register(BuiltInRegistries.STRUCTURE_POOL_ELEMENT, id, () -> codec)`).
- Into the pool: a data-pack **override of
  `data/minecraft/worldgen/template_pool/village/plains/houses.json`** with
  three of our entries (5x5, 7x5, 7x9, weight 12 each) in front of vanilla's.
  Works from a mod's resources; no Lithostitched needed. Collides with any
  other pack overriding that file (last wins).
- Test (`S9GameTest`): `Structure.generate` for `village_plains` (what `/place
  structure` does), snapshot region, `StructureStart.placeInChunk` per chunk in
  three orders, hash, restore.

## Findings that matter for the design

- The contract in the research note held: `Placer` queries box and jigsaws at
  `BlockPos.ZERO`, so footprint is per element; variety = several entries
  (codec fields), content variety is free.
- Vanilla house jigsaw name/target is `minecraft:building_entrance`; ours
  connected to the village streets with that on the first try.
- **Foreign spill into our box.** Vanilla tree features (`FeaturePoolElement`,
  zero-size boxes) put leaves into neighbouring boxes using the decoration
  random: 1 oak-leaf block inside one of our boxes differed between runs.
  Our blocks are not affected, but a hash of "our box" must treat leaves as air,
  and a real city must not assume it owns its air.
- **Vanilla itself is not order independent here**: with the same decoration
  random, 0-6 chunks per village differed (3-12 with a different random), even
  with leaves treated as air. Not investigated (likely features/trees and
  neighbour-dependent block updates). Only ours is covered by the claim.
- Pieces are saved with the element codec, so the saved start holds only
  `{width, depth, projection}` + position + rotation; regeneration after reload
  matched.
- Placement used `ServerLevel` as `WorldGenLevel`, and the gametest world is
  `FlatLevelSource`, seed 0, not the noise generator. Villages there are only
  produced by calling `Structure.generate` directly; the chunk-gen pipeline
  (`createStructures`, `applyBiomeDecoration`) was **not** exercised, nor was a
  noise-terrain village (slopes: rigid houses need a foundation fill; none is
  written). `getFirstFreeHeight` is a generator call in `Placer`, so the
  village layout depends on terrain; fine, it is the same for vanilla.

## Lithostitched compat

Feasible and done: Lithostitched 2.0.6 (`2.0.6-fabric-26.3`, Modrinth maven,
MIT) as `localRuntime`, behind `-Ps9.lithostitched`.

- Our element works inside its assembler: same tests pass, our blocks identical
  across orders, houses connected.
- **It changes vanilla villages**, as the deep-dive predicted (default
  `breaks_seed_parity: true`): same seed and start chunks gave 169/110/52
  pieces (17/17/6 ours) instead of 142/125/82 (13/15/9). So installing it
  alters every village layout, ours included.
- Not tested: `breaks_seed_parity: false` (the gametest run dir is wiped each
  run, so the config would need to be written by a test or a gradle task);
  `/locate`; a real noise world. A later test should set that config and
  compare piece lists against the no-Lithostitched baseline.

## What it means

Viable as a cheap demo and compat path; use it as in the note. Keep: fixed
footprint per element, own hash for content, write inside `chunkBB` only,
explicit `RandomSource` ignored. Needed in the real version: foundations on
slopes, entity/furniture placement via data markers or own code, a size ladder
of entries, and a test on noise terrain through real chunk generation.

## How to re-implement properly

Move the element and hash into `mod/main`; a planner-core call
(`seed, w, d -> house IR`) replaces the toy generator; keep the server test
(same start, 3 orders, hash inside our boxes, leaves as air) and add the noise-world
variant plus the Lithostitched config matrix.
