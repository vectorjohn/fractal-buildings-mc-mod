# S1 Biome footprint under world-gen mods

## Question

Vanilla is answered ([probe](../worldgen/terrain-biome-queries.md)): ~0.0025 ms per biome lookup, a fixed "priming" lookup before each query makes answers independent of order and thread. Open: (a) does priming still give identical answers in two orders and on 8 threads under TerraBlender (one climate tree per region), Lithostitched and Terralith? (b) What does a lookup cost in game, per km2?

## Result

**(a) Priming holds for Lithostitched and Terralith as is. Under TerraBlender with more than one region, one fixed priming query is NOT enough; prime inside the same region instead.**

| Mod set (all 26.3 Fabric builds exist) | unprimed: cells differing between orders (of 16,384, max over 4 grids) | single fixed prime | region-aware prime |
|---|---|---|---|
| vanilla | 2-15 | 0 | n/a |
| Lithostitched 2.0.6 | 2-15 | 0 | n/a |
| Terralith 2.6.5 (+ Lithostitched; adds 90 biomes) | 3-18 | 0 | n/a |
| TerraBlender 26.3.0.0.9, vanilla region only | 2-15 | 0 | n/a |
| TerraBlender + 2 extra regions (3 trees) | 2-15 | **2-14 cells differ** | 0 |
| TerraBlender + Terralith + Lithostitched, 3 trees | 3-18 | **2-10 cells differ** | 0 |

Each cell is 4 grids (2 seeds x 2 origins, 128x128 quart cells = 512x512 blocks at y=64), each compared in four ways: sequential vs shuffled (1 thread), vs shuffled on 8 threads, vs a second shuffle on 8 threads, and 8-thread vs 8-thread. "Differ" = at least one of those four is non-zero. The "must be 0" configuration (single prime, or region-aware under TerraBlender) is a hard assertion in the test: 0 differences in all six mod sets. Unprimed it fails (mutation check: 73 differences in the vanilla set).

Why a single prime fails under TerraBlender: each region has its own `Climate.RTree` with its own `ThreadLocal` last-leaf, and the region is picked per position (`IExtendedParameterList.getUniqueness(qx, qy, qz)`, a zoomed random layer; with 3 regions a 512x512 area was typically 83-88% one region and the rest another). The prime at (0,0) only primes the tree there. Fix, tested: before each lookup, ask the region index at the target (cheap), then look up a fixed **anchor in that region**. Anchor = a position in region r whose answer does not depend on which other region-r position primed first (picked by trying 16 candidates). A 9-point spread prime also gave 0 differences, but only by luck of hitting every region, and costs 9x; do not use.

Notes:
- All primed variants are self-consistent but break ties differently from each other (single vs region differ in up to 5 cells). So the **priming anchors must be fixed per world and mod set**, never changed between runs or sessions, or two generations of the same area could disagree at a tie.
- Terralith and Lithostitched did not change the biome source class: it is still `MultiNoiseBiomeSource`, with Terralith's biomes injected into the single parameter list (no TerraBlender regions of its own). So they behave like vanilla with more points, and a bit more ties (up to 18 per 16k cells).
- With a single tree everything about vanilla priming carries over. With TerraBlender the test must call TerraBlender's own per-dimension init (`LevelUtils.initializeBiomes`) on a generator the test built itself, otherwise the list is uninitialised and silently behaves like vanilla (my first TerraBlender run was a false pass for exactly this reason).

**(b) Cost** (server game test, server thread, `/proc/loadavg` 5-17 at the time because other agents were working; heavy lock held; numbers are noisy, ratios are not):

| Mod set | unprimed, 1 thread | primed (single/region), 1 thread | primed, 8 threads | primed, 1 thread beside 8 busy terrain threads |
|---|---|---|---|---|
| vanilla | 78 ms / 512x512 (4.8 us/lookup) | 152 ms (9.3 us) | 30 ms | 174 ms (10.6 us) |
| Lithostitched | 93 ms | 201 ms | 37 ms | 262 ms |
| Terralith + Lithostitched | 95 ms | 244 ms | 56 ms | 296 ms |
| TerraBlender, 3 trees (region prime) | 71 ms | 151 ms | 50 ms | 197 ms |
| TerraBlender + Terralith + Lith. (region prime) | 105 ms | 246 ms | 60 ms | 349 ms |

Per km2 (62,500 quart cells at one Y): **about 0.6 s on one thread (vanilla), 0.8-1.0 s with Terralith, 1.3 s worst case (TerraBlender + Terralith beside busy workers); ~0.11-0.23 s wall on 8 threads.** A 4 km2 city is 2.5-5 s of one thread, but the footprint is needed at plan time only, once per city, so it is not on the chunk path. In game the per-lookup cost is ~3.5-4x the probe's 0.0025 ms (priming doubles the lookups; the rest is JIT/cache, mod mixin wrappers and a loaded host): 9-15 us primed. This is the same direction as heights (2.2-2.5x). Cutting cost: sample on a coarser grid than the quart grid (a city plan does not need every 4x4 cell; 16x16 blocks = 16x fewer lookups, ~40 ms/km2), or cache per region.

## Evidence

- Test: `mod/src/gametest/java/dev/fractalbuildings/gametest/BiomeOrderGameTest.java` (`primingKeepsBiomesOrderIndependent`, `lookupCost`), plus `tb/TbSupport.java` (registers 2 extra TerraBlender regions as full copies of the vanilla parameter points with one biome swapped, so they are as tie-prone as vanilla; exposes region index) and `RegionInfo.java`. It builds its own NORMAL-preset overworld generator, as S8 did, because the game-test world is flat.
- Raw output per mod set: `docs/research/spikes/s1-results/<modset>[-cost].txt` (include loadavg).
- Run: `flock <repo>/.claude/heavy.lock nix develop -c ./gradlew :mod:runGameTest -Ps1mods=terrablender,terralith,lithostitched` (output in `mod/build/run/gameTest/build/s1/`). Without `-Ps1mods` it is the vanilla baseline.
- Mutation: forcing the "must be order-independent" configuration to unprimed fails the test (73 differences, vanilla). Single prime under TerraBlender with 3 trees shows 2-14 differences (that row is a finding, not an assertion).

## What it means for the design

- `BiomeProbe` live implementation: prime before every lookup (vanilla, Lithostitched, Terralith); under TerraBlender prime with a per-region anchor. Detect TerraBlender at runtime (`IExtendedParameterList` on the source's parameter list, `getTreeCount() > 1`) behind a small adapter so we do not depend on it at compile time (the test uses a compile-only dep; the core's `BiomeProbe` interface stays unchanged).
- Anchors are part of the world's determinism: derive them from the seed and the region index, scan order fixed, never from wall-clock or query history.
- Budget a city footprint at 1 s/km2 single-threaded at quart resolution, or sample coarser.
- Not tested: other TerraBlender consumers' real regions (BYG, Biolith); data-driven regions; the Nether/End; biomes at the surface Y rather than y=64 (same code path); a real chunk-gen worker thread (we simulated busy workers with `getBaseHeight` loops).

## How to re-implement properly

Production `BiomeProbe` in `mod/`: wrap `biomeSource.createResolver(sampler)`; `prime(qx,qz)` = region lookup (if TerraBlender) then `resolver.getNoiseBiome(anchor)`; make the test above a regression test over the mod sets the project claims to support, with the dependency setup below.

## Mod-dependency setup (for S2 / S7, reusable)

`mod/build.gradle` (bottom): property `-Ps1mods=<slug,...>` adds `maven.modrinth:<slug>:<version>` as `runtimeOnly` from `https://api.modrinth.com/maven`, versions pinned in a map (`s1Versions`). Gotchas:
- Loom 1.18 is non-remapping: plain `runtimeOnly` works, mods on the classpath are loaded by Fabric Loader (check `FabricLoader.isModLoaded`).
- Modrinth maven resolves a **version number** that exists for several loaders to one of them (TerraBlender `26.3.0.0.9` gave the NeoForge jar, silently not loaded). Use the **version id** (`xirJYe1V`) when in doubt, and check the log for the mod in the loaded list.
- Terralith requires Lithostitched; TerraBlender needs Fabric API (already there).
- Jars land in `~/.gradle/caches/modules-2/files-2.1/maven.modrinth/`; nothing is committed.
- A test that needs a mod's API compiles against it with `gametestCompileOnly` and is reached through an interface by reflection, so vanilla runs never load it. A mod entrypoint (`"terrablender"` in the gametest `fabric.mod.json`) is only invoked when that mod is present.
- The game-test run directory is cleared each run: write results to `build/...` and copy them out in the same shell command.
