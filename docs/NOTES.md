- 1.4 (2026-10-08): Structure blocks more than 8 chunks from the start chunk are silently never placed (`createReferences` scans ±8 against the start's bounding box, +12 if terrain_adaptation≠none); only jigsaw validates this (horizontal ≤128, ≤116 with adaptation).
- 1.4 (2026-10-08): One `StructureStart` per `Structure` per chunk (`ChunkAccess.structureStarts` is a Map keyed by Structure).
- 1.4 (2026-10-08): `BiomeSource.getNoiseBiome` is gone in 26.x: use `biomeSource.createResolver(climateSampler).getNoiseBiome(qx,qy,qz)` or `createResolverForChunk(...)` for batched volumes.
- 1.4 (2026-10-08): Biome lookups are order-dependent at exact climate ties (`Climate.RTree` thread-local `lastResult`, about 0.05% of cells); for deterministic results, run a fixed non-tie priming lookup before each query (probe: 0 diffs across orders and threads).
- 1.4 (2026-10-08): `ChunkGenerator.getBaseHeight(x,z,type,heightAccessor,randomState)` is pure and thread-safe; it costs about 0.2 ms per column on vanilla overworld (full-column density scan), includes aquifer water, and excludes beardifier, carvers and features.
- 1.4 (2026-10-08): The `postProcess` random for structure pieces is seeded by the structure's index in the registry within its generation step, so other mods' structures change it; derive piece randomness from our own hash.
- 1.4 (2026-10-08): `/locate` only handles `RandomSpreadStructurePlacement` and `ConcentricRingsStructurePlacement` (instanceof); a custom placement must subclass one of them to stay locatable.
- 1.4 (2026-10-08): `NoiseBasedChunkGenerator` is final; Fabric API has no overworld biome injection (only `NetherBiomes`/`TheEndBiomes`) and no structure API; surface rules are now `material_rule` / `material_condition`.
- 1.4 (2026-10-08): Measured in game: a structure piece reaching 20 chunks east of its start chunk placed blocks only in chunks dx 0–8 (silent clip confirmed).
- 1.4 (2026-10-08): Measured in game: structure-start piece building runs with max concurrency 1 per dimension (serial `worldgen` lane, hopping across Worker-Main threads); a 20 ms build per start adds ~20 ms wall time each.
- 1.4 (2026-10-08): `getBaseHeight(OCEAN_FLOOR_WG)` matches real generated ground in 98.2% of land columns (p99 |err| 2; seed 12345, 576 chunks); `preliminary_surface_level` is ~12–15 blocks below ground (p90 |err| 17) but 50× cheaper (0.0085 ms/col).
- 1.4 (2026-10-08): Any generator that isn't `NoiseBasedChunkGenerator` gets a level `RandomState` built from `NoiseRouterData.none()` (`ChunkMap.<init>`), which breaks `/locate`, biome lookups and structure climate sampling unless mixed in.
- 1.4 (2026-10-08): Overworld surface rules only run where `blockY >= floor(preliminary_surface_level) + surfaceDepth - 8` (`above_preliminary_surface`); a terrain cut deeper than that is bare stone unless `preliminary_surface_level` is wrapped too.
- 1.4 (2026-10-08): Client game test with a normal world: `context.worldBuilder().setUseConsistentSettings(false).adjustSettings(c -> c.setSeed("..."))`; run server code with `world.getServer().computeOnServer(server -> ...)`; `level.getChunk(x,z)` there generates to FULL (576 chunks ≈ 13 s under lavapipe client).
- 5.x deep-dive (2026-10-15): In 26.3 `preliminary_surface_level` is not a noise-router slot; it is a registry DF read only by the `chunk_surface_level` entry (router slot, drives material rules) and `Aquifer.Config.surface_level`. Wrap those two slots plus `final_density`, not the shared entry, or the coarse height screen gets wrapped too.
- 5.x deep-dive (2026-10-15): 26.3 `RandomState.getSampler(df)` / `samplersWithContext(ctx).sampleValue(df, x, y, z)` compiles any `DensityFunction` on demand (locked compile, `ConcurrentHashMap` cache keyed by the function), so a captured pre-wrap `final_density` can still be sampled; `getBaseHeight` itself always reads `settings.noiseRouter().finalDensity()`.
- 5.x deep-dive (2026-10-15): Lithostitched (2.0.6, 26.3) wraps the router by replacing it inside the shared `NoiseGeneratorSettings` in `ChunkMap.<init>`, so `getBaseHeight` and structures see wrapped terrain; `wrap_aquifers` exists only from 2.0.6, and its `JigsawStructureMixin` reroutes every jigsaw structure through its own assembler.
- Track 8 (2026-10-16): 26.3 precomputes stronghold rings at `ServerLevel` construction (`ChunkGeneratorStructureState.ensureStructuresGenerated` → `generateRingPositions`): RNG draws and `random.fork()`s happen on the calling thread, biome searches run as `supplyAsync` on `Util.backgroundExecutor()`, and `getRingPositionsFor` `join()`s; not persisted. A model for off-lane precompute.
- Track 8 (2026-10-16): `Mth.getSeed(x, y, z)` (`@Deprecated`) hashes coordinates only, no world seed; `RuleProcessor` and `StructurePlaceSettings.getRandom(pos)` use it, so template processor variation is identical across worlds (and `getRandom(null)` falls back to `Util.getMillis()`).

- Jetties (upper storey wider than the one below) under IR `fb-scene/1` and the 3.9 invariants (2026-10-18, read from `Invariants.java` and `IrValidator` rules, not run): representable, since `ir-valid` only requires volumes inside `bounds` and a resolvable `parent`, never a child inside its parent's footprint. `no-gap-below` only checks columns of volumes whose min y ≤ storey 0's y, so an upper volume starting above storey 0 is skipped and its overhang is not flagged; one tall volume spanning the overhang columns from y 0 would be. `no-floating` is per 6-connected component, so an overhang joined to the walls below through its slab passes. `roof-covers`/`roof-closed` are per roofed volume and scan up to any roof voxel, so an unroofed lower volume under the jetty is fine. `in-lot` still flags overhang past the lot edge. Nothing checks how far an overhang cantilevers: a generator rule (1–2 blocks), not an invariant.

- Tall fixture (`TestMassings` `tall50`: 28x28, 50 storeys, ~60k voxels): a 16-cell gallery page takes ~3 s in SwiftShader (front-left/top; cutaway ~1.3 s), load ~2, so no exterior-only mode was needed (`?exterior=1` exists in gallery.ts anyway). 60 storeys of >= 4 blocks exceed y 319 on sloped ground (V1PropertyTest fails the world-height check), hence 50.
- City block (4.6): units must not touch except by a shared 1-block strip of >= 3 (M6), so a side column hangs from a corner unit and is >= 2 narrower than it (else it meets the next unit of the row by one cell); a "strip" check for openings must only count storeys both masses span (above the lower unit the wall is an outer wall with windows). `fractal-cli diversity --type block --seeds 0..255 --lot 64x48 --style medieval`: Jaccard 0.619, 239 signatures; shell time 4.9 ms mean, 10.8 ms p95 (load ~20, not quiet).
- House program (4.6): `RoomProgram` has storey-aware `use/hooks(.., Where, ..)` and `newBand(storey)` (defaults delegate, other types unaffected); the interior pass keeps hooks 2 cells away from a core (ring of 1 + `near`), so `HouseMassing.roomy` demands >= 5 wall-side free cells per core-served mass. 2048 house cases: 1230 multi-storey, all with a bed upstairs; 71 % of them 2+ bedrooms, 62 distinct (volumes, storeys, bedrooms) shapes.
- Test lots (`TypeLimits.testLots`) are in the front frame (width along the front); `TypeLimits.oriented` turns one that does not fit for east/west fronts (used by `V1Case` and the CLI matrix), so narrow deep types (shop) work with all four fronts. `MainTest` check/bench calls pin `--types house` so other types' case counts don't move them.
- Interior pass: custom facade layout kinds other than window/blank/door reserve the whole bay's inside cells, so a type can keep a front row uncut (shop: `pier`/`shopfront` bays keep the front room one room across the full width).
- High-rise (4.6): spec storeys 20..60 are capped by the type's massing to what fits under `maxHeight` (5 + 4 per storey + 3), so towers on high ground are shorter; the type's shell takes ~4 ms mean / 14 ms p95 (flat 60 storeys at 44x44 included), check ~8 ms; `V1PropertyTest` for it runs 48 cases in a second or two.
- Facades (4.4): `./gradlew :planner-core:test --tests '*FixtureDumpTest*' -Dfb.dumpFixtures=...` needs `--rerun` (the test task is otherwise UP-TO-DATE and writes nothing). Facade decor outside the wall plane must be checked against `Decor.outFree` (envelope, free air, not in front of a door/window); `assemble` throws on boxes outside the envelope.
- Front steps (4.8): `InstancePassV1` adds STAIR blocks on FOUNDATION outside the footprint; a test mutant that removes only the STAIR tops still passes `entrance-reachable` (the foundation tops form a flight one lower), remove the whole flight to test the invariant.
- Roofs (4.3): `no-floating` is 6-connected, so a 1/1 stair of single ROOF voxels counts as floating; the roof pass fills each higher column down to the lower neighbour's level (steps touch face to face). Heightfield closure (fill beside lower neighbours and open air, cap beside higher masses' walls) makes roof-closed hold for any field, so forms are purely aesthetic choices.
- Roof groups (4.3): masses with the same `to` that overlap (not party walls) share one heightfield; columns under a strictly higher mass are not roofed (the higher mass's roof covers them); `RoofPass` overhang sits at the top-slab level (y = base - 1) on envelope columns no mass stands on.
- Temple (4.6): lots are w x d, so a long thin type given 15x25 with front east/west is 25 wide x 15 deep and fails the spec policy; `V1Case.draw`, `cli Matrix.oriented` and `ReplayTest` turn such a lot (front moved to the matching side or w/d swapped); other long thin types (hall, wall) get the fix for free.
- Temple (4.6): `RoomProgram.use(role, massKind, area, draws)` (default delegates to the 3-arg one) lets a program tell nave from apse; open masses all have role HALL otherwise. Hook kinds `altar` (apse only, back third) and `bench`.
- Temple (4.6): a core can't sit in a front tower with `MassingOps.core` (its candidates are all next to the strip to the nave behind), so the temple builds its own `Core` two rows in from the entrance row and two short of the back strip.

- Tower: `TowerType` ignores the style's `groundExtra` (a 5-high ground storey needs a core of 6, more than a 7-wide tower holds).
- Snowy style window density (120 flat 20x20 houses, windows per bbox facade area 2(sx+sz)sy): 0.0128 vs plains 0.0266; all snowy pitched roofs are 2/1.

- Hall (4.6): a core can't stand in an open mass (M8), so halls put stairs in small tower/annex masses; `MassingOps.core` finds nothing for a mass whose back wall is a shared strip, use `coreAnywhere`.
- Hall (4.6): every extra ground-floor exterior DOOR gets its own front-step flight (4.8); on slopes the lot margin cannot hold several, `entrance-reachable` then fails (3-9 of 200 cases for 3-wide arcade doors). Use window-kind openings for decorative arches.
- Hall (4.6): `RoofPass.run(c, RoofStyle)` lets a type lower the pitch for wide spans (a 1/1 gable over a 36-wide hall rises 18); 200x200 hall: generate 8-72 ms, invariant check 42-281 ms (host load ~40).
- `V1Case`: lots wider than 120 use noise terrain, the recorded crop is only ~2000 x 2000 blocks.
- Wall type (4.6): the passage is an `open` one-storey mass so it is one room; gates are DOOR-role boxes 3x4 (closed gate leaves) with their own `Opening`, not 1x2 doors; the second (town) gate is a second `FacadePlan` entrance on the same mass (`others`), not a second entrance mass. - Wall type (4.6): wall-walk door sits one block above the tower floor (tower storey 1, y = slab + 2) so you step up onto the curtain's ROOF layer; `RoofPass.run(c, RoofStyle)` and an `OpeningPass.run(c, doorCutter)` overload are the additive helpers it needed.
