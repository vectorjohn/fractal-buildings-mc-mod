- SK (2026-10-21): cell skeletons are `Skeletons.build(seed, RegionView, Cell, CoarseProbe, DistrictGrid)`, one per member cell, merged by `Skeletons.plan`/`assemble` (any order, fresh probe: same JSON). - SK (2026-10-21): vanilla terrain read at 32 blocks is rough: inside a city disk 34 % (river window, r700: 457 urban, 232 steep) to 61 % (w1-mixed, r800: 271 urban, 426 steep, 265 water) of the dry columns have a 4-neighbour more than 16 higher or lower, so the urban mask is patchy. `CoarseTerrain.STEEP_PER_32` is the one constant to relax if cities come out too fragmented; hashed +-20 white noise on every column (the `BiasedCoarseProbe` test) makes nearly every column steep, which is why the bias test counts cell gates, not exits.
- SK (2026-10-21): `fractal-cli city` (`--cell CX,CZ` through the join rule, or `--site X,Z,TIER,RADIUS`) plans a whole settlement skeleton in 0.05 to 0.6 s (a 5-cell metropolis on the coarse world dump: 130 ms); a recorded dump must cover the footprint plus 64 blocks (reads outside throw), so sites near a dump edge need a bigger window.
- ROADS (2026-10-21): a district's lots depend on the whole settlement's `RoadNetwork` (all member skeletons), not only on nearby cells: a source that serves many tiles must memoise `network()` (`SkeletonSource.Direct` does; the interface default rebuilds it per call).
- ROADS (2026-10-21): skeleton landmark ids are all `l?` until `Skeletons.assemble` numbers them; inside `Districts` compare landmarks by identity, never by id.
- ROADS (2026-10-21): a stored `Street` is exact: its points are the vertices plus both columns of every height step, and `Grading.road(points, ys, width, exact)` interpolates between them; never re-grade a street from its points alone (each tile would get a different profile).
- ROADS (2026-10-21): `Grading` bridge decks are lower bounds (surface + 3), not fixed levels; the road may rise over two close spans rather than step.

## Tests and known flakes
- Integration checkout (2026-10-22): never run two Gradle builds in one checkout at once. `:planner-core:test` takes ~10 min serially (settlement tests dominate), and a second `test` run wipes `planner-core/build/test-results/test/binary` while the first is still writing or reading it, so the first fails at report time with `EOFException` / `KryoException: Buffer underflow` and no failing test in the XML. Every Gradle run in the integration checkout, post-merge or ad hoc (reruns, checks, `test-all.sh`), must hold `flock <repo root>/.claude/merge.lock`; if a run already died this way, delete that `binary/` dir and rerun under the lock. Locked rerun 2026-10-22: 603 tests, 0 failures, 10m19s, loadavg 3-7.
- Merge lock (2026-10-25, process change): `scripts/squash-merge.sh` holds the merge lock only for clean check + squash + commit, releases it (`flock -u 9`), then runs post-merge tests via `scripts/snapshot-test.sh` on a detached worktree `.claude/worktrees/postmerge-<sha>` (removed after). The rule above still holds for any Gradle run inside the integration checkout itself. Two merges in quick succession can each pass alone and fail together; the next merge's post-merge run and the batched heavy run catch it.
- Server game test isolation (TESTISO, 2026-10-25): tests that place settlements write absolute world coordinates, and several share a town (flat seed 6 town, seed 5 village, the fixture town). Wrap such a test in `TestArea.run(helper, boxes, body)` (gametest `worldgen/TestArea.java`; boxes from `TestArea.boxes(level, planner, chunk, structures...)`; `@GameTest(maxTicks = TestArea.TICKS)`): it waits until the boxes' chunks have their entities loaded, clears blocks and non-player entities, runs the body, clears again, all in one tick. `runGameTest` deletes `mod/build/run/gameTest/world` first. Fixed flakes: Gameplay villager counts/ids (OrderGameTest left seed-5 villagers, plus hidden entity sections), `WorldgenGameTest` fixture town "world blocks differ" (a previous run's or older generator's blocks in unclaimed cells, seen by the uncleared ascending pass), `TeleportHoldGameTest.longJumpWaitsForFullChunks` timeout (VetoGameTest blocks the server thread ~50 s; the hold's 30 s deadline is wall time).
- Isolation checks (TESTISO): `./gradlew :mod:runGameTest -Pfb.serverTestOrder=reverse` (or `shuffle:<seed>`) reorders the server test classes; `-Pfb.gametestFilter='fractalbuildings-test:worldgen_game_test_*'` runs a subset. Before the fix, reverse/shuffled orders failed 5 of 6 runs (shuffle:4 passed). Anything that waits on wall time or other threads must not lean on `maxTicks` (ticks run back to back): use `TestArea.waitThen(helper, maxMillis, ready, verify)` with `maxTicks = TestArea.TICKS`.
- Flake (verifier, 2026-10-25): `TeleportHoldGameTest.timeoutTeleportsAnyway` "Didn't succeed or fail within 400 ticks" on claude/p6-testiso a59ace4 (TESTISO harness), `:mod:runGameTest -Pfb.serverTestOrder=shuffle:2026`; 1 of 8 runs, the 2 identical reruns passed. - Flake (verifier, RAILFIX 2026-10-25): `RoadNetTest.coldChunksAskedByManyThreadsComputeEachRouteOnce` failed once in a full `:planner-core:test --rerun` (claude/p6-railfix 3e0510df, load about 50, run possibly overlapping another Gradle run in the same worktree; failure message lost to the overlapping run), passed on the identical rerun; 1 in 2 runs seen.
- RoadNet flake diagnosed (assistant, roadnet-flake 2026-10-25): it is a real race, not the concurrent-Gradle artifact. `RoadNet.flight` removes its in-flight future (`finally`) before `BoundedCache.get` stores the value, so a thread that misses the cache just before the store and claims the flight just after the remove computes the route (or cell) again. The result is extra exact reads, always above the single-thread count (seen +668, +104, +501, and +4 in another worktree). Answers are unaffected (the function is pure and the cache keeps the first instance), so worldgen determinism is safe; the cost is duplicated work. Rates: 1 failure at load 50 with 8 threads, 0 of 30 alone, 2 of 20 with 64 threads; a forced interleaving reproduces it in 41 of 200 trials. Fix: store into the cache before removing the flight, and re-check the cache after winning the claim.
- Flake (verifier, p7-windows 2026-10-25): viewer e2e `district.spec.ts` at loadavg 95-100 (claude/p7-windows 5dd7fc27, viewer inputs identical to run-phase6): "sample district: faces mesh, fly camera, three stops" hit the 30 s test timeout in `page.screenshot` in `scripts/test-all.sh --no-client` and passed on an identical rerun; "large synthetic district ... loads within budget" failed both runs on the timing budget (`loadMs` 23059 vs < 20000). - Viewer e2e under load (assistant, viewer-flake-qs 2026-10-25): the `district.spec.ts` failures at loadavg 95-100 are load, not a slowdown. A/B on the same box, alternating, `--workers=1`, load 68-89: today's viewer loads the 6x6 synthetic district in 12.6 / 13.5 / 19.0 s, the V2 viewer (a958b061, 2026-10-21) in 11.3 / 11.6 / 14.7 s, with 3 % more voxels now (375k vs 365k); a full suite run at load 64 took 7.0 s; the V2 log had 5-7 s at load 25.
