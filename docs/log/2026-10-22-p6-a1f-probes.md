# P6 A1F: probe follow-ups (sub-blocks, live biome, bracket, copies, mod/logs)

Branch `claude/p6-a1f-probes`, follow-up to [A1](2026-10-22-p6-a1-probes.md).

## What changed

- **Sub-block fills: tried, measured, dropped.** Lazy 4x4-column blocks (16 per chunk, memo with a block mask, windowed fill per
  block) were parity-exact (all tests green) but slower: a district read touches 13 of the 16 blocks of a chunk on average
  (6,387 block fills for 500 chunks), so it pays 13 window/NoiseChunk setups where one served. Cold district (d), mean of 5
  districts, load 7: **5.0 s** against **3.1 s** for the whole-chunk windowed fill (both with the then-expensive above-check, below).
  "23 columns per chunk" is spread over nearly every block, so a finer fill cannot skip work. The code is not kept.
- **Live biome surface** now comes from the chunk memo: `LiveTerrainProbe.surfaceY` (`ColumnMemo.surface`, floor + water). Region and
  coarse lattice biome reads keep a second `LiveBiomeProbe` on `SparseColumns` (single columns), because a 64-stride read would
  otherwise fill a whole chunk for one column. `lazyBlockReadsMatchColumns` checks district biome == sparse biome.
- **Bracket blind spot closed (to a stated resolution).** `ChunkFill.Batched.window` now also samples the final density at the
  chunk's two diagonal corner columns every 16 blocks from the window top to the world top; any positive value sends the chunk to the
  full scan (`ABOVE_HITS`). It is not a proof: a solid feature thinner than 16 blocks, or missing both columns, is still unseen.
  Vanilla has none (72 + 24 random chunks, 0 hits). Test `overhangAboveWindowFallsBack` bends the density router (a 16-thick slab at
  y 224 to 239) and compares with `getBaseColumn` on the bent terrain; with the check disabled it fails (mutation run).
  Cost matters here: a first version with a `DensityVolume` over the above-window range cost **4.9 ms per chunk** (a tall volume
  costs by its extent, not its point count: about 8 us per interpolation corner); point samples through the window's existing
  `NoiseChunk` cost **0.34 ms** (about 14 us per point). Point and volume values were identical (max diff 0 on 640 points).
- **`SparseColumns.get` returns a clone**; `surface/floor/water` read the cached array without leaking it. Test `sparseColumnsReturnCopies`.
- **`mod/logs` untracked** (`.gitignore`, `git rm --cached`).
- Side finding: windowed margin 16 or 8 (instead of 32) is not safe to shrink for speed: 45 and 67 of 120 random chunks fall back
  (still 0 mismatches, so the bracket check works) and it gets slower.

## Is 300 ms reachable?

Not by fill speed. 431 chunks x 1.9 ms = 820 ms is nearly all of the 900. Measured pieces of a chunk fill: window 0.1 ms,
above-check 0.34, scan (density volume + aquifer per block) 1.5. A quiet machine may give 1.5x, not 3x. Reaching 300 ms on one
thread needs about **150 chunks per district** (or 0.7 ms per chunk). So A6 would have to cut the footprint, not the per-column
count: the 10,124 columns spread over 431 chunks (a ~330 m square around a district) are what costs; fewer, denser reads (e.g.
grading and lot probes confined to the district's own ~150 chunks, shared border chunks via the memo) matter more than
fewer calls (21k calls are free once memoised). Other routes: B4's workers (n workers divide it), or accept ~0.9 s cold with
background warming. B8 re-measures on a quiet machine.
