# TESTISO: server game test isolation (absorbs DETFLAKE)

Branch `claude/p6-testiso`, lead-coder, 2026-10-25.

## Symptoms

- (a) `WorldgenGameTest.fixtureTownPlacesIdenticallyInAnyChunkOrder`: "world blocks differ in another chunk order", rare, with the ledger digest equal.
- (b) `GameplayGameTest.villagersAreOffInTownsAndWhenConfigured` / `hooksAndLootAreTheSameInAnyChunkOrder`: wrong villager counts or ids, about 1 run in 3.
- (c) Results depend on test order (sorted-by-name order failed Gameplay 8 of 8).

## Causes (each reproduced)

1. **Shared absolute areas, varying start order.** Placement tests write real world coordinates and several share one settlement (flat seed 6 town: Worldgen, Gameplay, Warming; seed 5 village: Gameplay and Order; the fixture town: Worldgen and its mutants). Each game test starts in the first tick its own test-structure chunks are entity-ticking (`GameTestInfo.tick`), so the order differs between runs. `OrderGameTest` placed the seed-5 village (villagers on) and never removed the villagers; mutants left the fixture town in place; the ascending pass of `placesInAnyOrder` and the first pass of the Gameplay tests did not clear first.
2. **Hidden entity sections.** A villager added to a chunk whose FULL promotion is still queued lands in a HIDDEN section: scans and discards do not see it but its UUID stays taken, so the next spawn of that (deterministic) UUID is dropped ("UUID of added entity already exists").
3. **The world persisted between runs.** Fabric's runner opens `mod/build/run/gameTest/world` as it is, so chunks, villagers and POIs of the previous run (or of an older generator's run in the same worktree) were loaded.
4. **TeleportHold long jump** ("released with full=false timedOut=true", seen in the same reordered runs): the hold's 30 s deadline is wall time and VetoGameTest blocks the server thread about 50 s in one tick, so the hold could time out before any chunk loaded.

No generation order-dependence was found: the ledger digests were equal in every failure, and the diffs only showed unclaimed cells.

## Evidence

- Diagnostics first (3a8449b): a world-hash mismatch now lists each differing cell (position, expected, actual, claimed state or "unclaimed") and the order; villager mismatches list ids with positions.
- Old harness, fresh world each run, 8 runs: default order 2/2 pass; `reverse` x2 and `shuffle:1..4`: 5 of 6 failed (shuffle:4 passed; Gameplay villagers in all 5, TeleportHold long jump in 3). The failing messages show the Order test's leftover villagers (12 ids against 10).
- Old harness on a world left by the pre-STAIRS commit (7eca64c^), the B8 situation: fixture town failed with `2 cells differ: 32,71,151 expected stripped_oak_log actual air (unclaimed); 32,72,152 expected stone actual air (unclaimed)`.
- New harness on the same old world, with the world wipe switched off on purpose: all 35 pass (the pre-clear alone handles stale blocks).
- A probe that left a building start in place and ticked it 600 ticks (chunks simulated) changed nothing, so physics on leftovers is not the mechanism; stale blocks in cells the current generator does not claim are.

## Fix (8eb25dd)

- `TestArea` (gametest `worldgen/`): `run(helper, boxes, body)` tickets the boxes' chunks (DRAGON tickets, radius 2, ref-counted across tests), waits until every chunk has its entities loaded and visible (bounded by 10 min wall time, not ticks: the test server runs ticks back to back), then in one tick clears blocks and non-player entities, runs the body, clears again (also on failure) and succeeds or fails the test. `boxes(level, planner, chunk, structures...)` gives the start boxes.
- Worldgen (placement and mutants), Gameplay (three placement tests), Order (all seven) and Warming (`warmedAndColdWorldsPlaceTheSameBlocks`) use it, with `maxTicks = TestArea.TICKS`.
- `runGameTest` deletes the test world first.
- TeleportHold: the long jump's hold gets a 10 min deadline (the timeout has its own test); `timeoutTeleportsAnyway` clears `testLoad`/`testReleased` right after its teleport.
- Isolation tools: `-Pfb.serverTestOrder=reverse|shuffle:<seed>`, `-Pfb.gametestFilter=<selector>`.

## Round 2 (verifier: `timeoutTeleportsAnyway` flake)

- Cause: the test waited for a 300 ms wall-clock timeout under `maxTicks = 400`; the game-test server runs ticks back to back, so 400 ticks could pass first ("Didn't succeed or fail within 400 ticks"). The same pattern (a wall-time or other-thread wait under a tick budget, through `helper.onEachTick`) was in all four TeleportHold tests that wait.
- Fix: `TestArea.waitThen(helper, maxMillis, ready, verify)` waits through a `GameTestSequence` bounded by wall time (10 min here) and registers nothing per tick; the four tests use it with `maxTicks = TestArea.TICKS`. Other server tests checked: Veto and Warming wait synchronously inside one body (no tick budget involved); `deadPlayerDropsTheHold` waits 5 ticks for tick-driven behaviour (correct as is); the TestArea tests were already wall-clock bound.
