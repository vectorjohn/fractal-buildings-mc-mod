# CASCADE step 6 (B1): reads pool size, measured on a quiet beebox

Branch `claude/assist-p6-cascade-6`, plan [jflazy.md](../plans/jflazy.md) "Step 6". Measurement only; no product code changed.

## Did
- Six `scripts/perf.sh --world-only` runs on beebox at c468dd41: `-Dfractalbuildings.readThreads=N` for N = 4 (today's default there), 8 and 11, two runs each, interleaved. Each run went through `scripts/evidence.sh p6-cascade-6-n<N>-r<k> scripts/remote.sh -- ...`.
- A driver script (scratchpad, not committed) sent each job only when beebox had nothing running or queued, ran `scripts/quiet-check.sh --beebox` before and after, and accepted a run only when all of these held: it ended `perf: quiet host`, the after-check was QUIET, `world.json` was written, and `jcmd VM.system_properties` on the running mod server showed the intended N.
- Results: [regionperf-decision.md](../review/regionperf-decision.md) section 7, "Reads pool size"; a dated line in PERFORMANCE.

## Verified
- All six runs were valid, and all of them included the arrival pair (`world-arrival-*.json`).
- Slowest cold chunk: 34.9 s (N = 4), 30.8-30.9 s (N = 8), 30.5-30.7 s (N = 11).
- Cold arrival: 52.3-52.8 s, 47.6-47.9 s, 46.5-47.7 s.
- Worst flight tick: 0.87 / 5.32 s, 4.68 / 4.25 s, 0.28 / 0.39 s.

## Surprises
- **`JAVA_TOOL_OPTIONS=-Dfractalbuildings...` fails every perf run.** Every JVM prints the variable's value, including the vanilla base server, and `perf.sh` fails a base run whose log mentions "fractalbuildings". The first 18 tries (about 5 min each) were lost to this.
- Passing the property through an argfile works, because the JVM then prints only the file path: `JDK_JAVA_OPTIONS=@<file>`, with the file written inside the remote job.
- `scripts/remote.sh` does not pass environment variables to beebox, so the variable has to be set inside the remote command.
- The flight tick's 4-5 s mode always came at 1,978 blocks flown.

## For later
- If the default changes, measure in singleplayer (a client on the same CPUs) and on a smaller machine; only a 12-CPU dedicated server was measured.
- An `FB_PERF_MOD_JVM_ARGS` option in `perf.sh` that reaches only `:mod:runPerfServer` would avoid the argfile trick.
