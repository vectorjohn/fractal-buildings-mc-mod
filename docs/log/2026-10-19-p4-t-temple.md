# 4.6 temple type

Branch `claude/p4-t-temple`. `gen/v1/types/temple/`: `TempleType` (limits 13x22 envelope, 2-3 storeys, margins side 1 / front 2 / back 1, lots 15x25, 19x31, 25x38, 31x45, `maxGrade` 2), `TempleMassing`, `TempleFacade`, `TempleRooms`. One `r.add(new TempleType())` line in `Types.java`.

**Shape** (local frame, front north, all widths odd so the axis is a block column): front block first (porch, one open storey, or a 9-11 wide bell tower with its own stair core and 1-3 storeys above the nave) carrying the entrance; one open nave (9-17 wide outside, 8+ deep, 2-3 grid storeys of 4-6 blocks); optional pair of side chapels (open, one storey lower, `MassingOps.wing` on E and W); an apse (narrower, sometimes one storey lower) whose walls start at 2/3 of the building depth, so the altar hook, which the room program puts in the apse only, is in the back third. Backs off (no tower, no chapels, fewer storeys, height clamped to `maxHeight`) and the last resort fits every legal envelope.

**Shared-code touches (additive):** `RoomProgram.use(role, massKind, area, draws)` default method and the one call in `InteriorPass`; `V1Case.draw`, `cli Matrix.oriented` and `ReplayTest` turn a long thin lot when it only fits the other way round (the matrix has lots w x d and four fronts); `MainTest` asserts only ", failing: 0" and runs the 12x10 check/bench with `--types house` (same as T-highrise, keep either side).

**Tests:** `TempleTypeTest` (door on the axis and altar in the back third, each with a mutant that must fail: default facade, nave-as-sanctuary room program; nave open and 7+ wide inside, axis symmetry, tower above the nave with stairs, massing contract for every height cap 6..40, diversity floors at ~80 % of 256 measured: towers 54, chapels 80, stepped apse 158, nave widths 5, heights 4, depths 16); `V1PropertyTest` temple (480 cases) green; golden `golden/v1/temple.txt`; `check --types temple --seeds 0..49`: 6400 cases, 0 failing. `:planner-core:test :cli:test` green after merging `claude/run-phase4` (R, S in).

**Gallery:** presets `temple-plain` / `temple-medieval` (25x38, noise) and `temple-flat` (31x45 flat), five cameras, all 0 violations. Seen: axial plan from the top (porch, wide nave, chapels, apse), centred door, gable nave with hipped chapels and front steps; tower seeds look tall and house-like because windows repeat per storey (known issue, REVIEW entry).

**Surprises:** the core helper can't place a core in a front tower (see NOTES); height cap 6 broke an early version (nave height now clamped).

**Correction (4.10 gate pack, 2026-10-19):** the temple's own orientation code described above (`cli Matrix.oriented`, the lot turning in `V1Case.draw` and `ReplayTest`) was removed in round 3. Lots are now turned by the shared `TypeLimits.oriented(lot, front)` (from the shop step), which `Matrix`, `V1Case.draw` and `ReplayTest` all call.
