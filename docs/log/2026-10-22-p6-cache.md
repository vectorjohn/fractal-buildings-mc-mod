# P6 CACHE: retention for in-flight and recently used tiles

Branch `claude/p6-cache`. From the B2 verifier: with 3+ players in different cities the active tiles exceed the caps
(buildings/ground 32, plans 64, sources 64), their chunks interleave, and every chunk's `postProcess` / `HookPlacer` re-ran
`Pieces.buildings` (the generator for every lot, ~100 per tile) after another tile evicted the entry.

## What changed

- **Retention instead of a lease.** `FlightCache` and `BoundedCache` take `graceNanos` and `hardFactor`. An entry used within the grace
  (default 120 s, longer than a tile's chunks take to arrive) is not evicted for capacity, so the map may exceed its cap, but never
  `cap x hardFactor` (default 4): past that the eldest goes regardless. In-flight entries are protected by the same rule (created =
  used). Chosen over reference counts because nothing has to be released: a stuck worker, a crashed task or a forgotten `finally`
  can only hold memory for the grace period, and `TilePiece` / `HookPlacer` needed no change. The clock (injectable `LongSupplier`,
  `System.nanoTime`) decides only what is kept, never an answer.
- `WorldPlanner.Caches` gained `graceNanos`, `hardFactor` (the 7-int constructor keeps working with the defaults), `strict()` (no
  retention) and `forHeap(maxHeap)`: buildings/ground cap 32 up to 64 and plans 64 up to 128 as the heap grows, so that the hard
  ceiling stays near a tenth of the heap. `Caches.all(n)` is strict (the eviction tests rely on that). `WorldPlanners.create` uses
  `forHeap(Runtime.maxMemory())`; sources (settlements) are retained the same way.

## Evidence

- `WorldPlannerCachePressureTest.interleavedTileStreamsPastTheCapComputeEachTileOnce`: 12 tile streams x 20 interleaved chunks, cap 4:
  strict LRU 252 buildings computations, with retention 12 (one per tile); digests equal and equal to the order-test baseline.
  Also hard-ceiling, expiry, in-flight-joins-once and stuck-worker-releases tests with a fake clock. Mutation (retention check
  disabled) failed all four.
- `CacheMemoryTest`: a cached tile (plan + buildings + ground, metropolis, 30 tiles / 351 buildings) holds about **0.9 MiB** retained
  heap (26.6 MiB / 30). Ceiling with defaults: buildings/ground 128 tiles each, plans 256, so about 115 MiB for the building and ground
  memos plus plans, a few hundred MiB worst case on a big heap only if players really have that many tiles active within 2 minutes;
  typical (3 to 5 players) 30 to 60 tiles, 30 to 60 MiB. Not measured: the memory of a `SkeletonSource` road network (sources cap
  64, hard 256 settlements); only a metropolis is large.
- Existing order / parity / isolation / region / warming tests: see report for the run.

*Known issues:* the hard ceiling still evicts under extreme load (> 128 simultaneous tiles), where thrash returns; a server with
that many active tiles needs a larger heap. Memory above the cap is only released by the next lookup (no timer thread).
