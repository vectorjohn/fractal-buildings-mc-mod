# COLDTICK (6.37): the multi-second server ticks on cold arrival

Branch `claude/p6-coldtick`, lead-coder, 2026-11-02. Item: ROADMAP 6.37; polish lines COLDARRIVAL and 6.30 PORTALCOLD (1).

## Cause (stack evidence)
Vanilla's cat spawner. `ServerLevel.tickCustomSpawners` runs `CatSpawner.tick` every tick; it fires every 1200 ticks (first on tick 1), picks a random player, a spot 8 to 31 blocks away, and tests `level.hasChunksAt(spot +- 10)`. That test is `ServerChunkCache.hasChunk` (26.3 ServerChunkCache.java:256-260): true for any chunk whose holder has a FULL-level ticket, **generated or not**. The next call, `SpawnPlacements.isSpawnPositionOk` -> `Level.getBlockState`, then runs `ServerChunkCache.getChunk(FULL)`, which on the server thread is `managedBlock` until that chunk is generated. Vanilla chunks take milliseconds; a cold district chunk of ours takes seconds, so the whole server waits.

Stack (the perf worker, old code eb35c766 plus the new long-tick watch, arrival pass; every one of the 20 dumps of the stall is the same):

```
ServerChunkCache.getChunk(ServerChunkCache.java:146) <- Level.getBlockState(Level.java:365)
<- SpawnPlacementTypes$1.isSpawnPositionOk(SpawnPlacementTypes.java:44) <- SpawnPlacements.isSpawnPositionOk(SpawnPlacements.java:163)
<- CatSpawner.tick(CatSpawner.java:51) <- ServerLevel.tickCustomSpawners(ServerLevel.java:501) <- ServerChunkCache.tickChunks(...:398)
```

27.6 s and 24.2 s ticks (GC 344 / 303 ms of them), both on server tick 1200, the cat spawner's second firing. The perf world's arrival used to release the teleport hold at 30 s with nothing FULL, so on the perf worker the player was still standing in an ungenerated metropolis at tick 1200 (locally the arrival was done by then: the 52 ms). This is the COLDARRIVAL 9-11 s tick.

- **Arrival, today:** gone since TPHOLD15/TPABORT (the hold now waits for the 3 x 3 to be FULL, so the area is nearly done by tick 1200). Every quiet perf-worker arrival since then is under 1.3 s; my three: 836 / 929 / 899 ms.
- **Flight row** (`mod.flight.tick.max.ms`, bimodal 0.3 s or 4 to 8 s, PERFORMANCE "Watch"): inferred to be the same. The worst flight tick of the 8.0 s run is flight tick 1199 (1978 blocks), the cat spawner's firing; the elytra flier is always ahead of generation. My 7 flight runs on the perf worker (3 quiet, 4 diagnostic) stayed under 0.91 s, so I have no stack of a flight stall.
- **Portal 6.35 s** (1 run in 6 at 6824675f, "about 8 s after arrival"): not reproduced in 10 held runs (3 perf worker, 4 second worker, 3 local) on today's code; no stack. Inferred to be the same mechanism (PortalHold releases at INITIALIZE_LIGHT, so the exit area is still generating after arrival, and the spawner fires once a minute).

## Fix
`CustomSpawnerReadyMixin` wraps the `ServerLevel.hasChunksAt(IIII)Z` call in `CatSpawner.tick` and `PatrolSpawner.tick` (the two custom spawners with that guard): it also needs every chunk of the box FULL now (`ReadyChunks.allFull`, `getChunkNow`, never loads), otherwise the attempt is skipped. Generated blocks are unchanged (cat and patrol spawns are gameplay, from the level's own random). On the old code plus the fix (the perf worker, beside another job, not a measurement) the two arrivals that had stalled 24-27 s peaked at 2.1 s and 1.3 s, both while the player was still at spawn.

## Diagnostics added (kept)
- `LongTickWatch` (gametest perf package): from 1.5 s into a tick (or the gap between ticks) it logs the server thread's stack every second (up to 20), once the running chunk workers and our pool threads, and GC time plus heap since the tick began; every stall of 1 s or more gets a `long tick #N ended` line. Used by `PerfServerHarness` (`[PERF-DIAG]`, flight, settle and arrival; not the synchronous block rows) and `PortalColdHarness` (`[PORTAL]`, replaces its one-shot dump).
- `scripts/perf.sh`: `FB_PERF_MODES=arrival|main` runs one pass only; `FB_PERF_ARRIVAL_RELEASE=plan` releases the arrival hold once the destination is planned (into chunks that are not FULL). Diagnostic, never a measured run.

## Other findings
- The perf worker's server JVM has a 2030 MB max heap (25 % of the job's cgroup limit), the local host 16 GB; `WorldPlanner.Caches.forHeap` sizes the planner caches from it. Not the cause here (GC 0.3 s in a 27 s stall; the local 2 GB 12-CPU runs had no stall).
- Vanilla reads that generate synchronously remain: `VaultBlockEntity.setChanged` -> `updateNeighbourForOutputSignal` at the spawn area's edge (2.1 s, the perf worker under load), and a 1.6 s first tick of a hopper (`ItemStorage` class init, Fabric transfer API). `WanderingTraderSpawner` reads heights near a player without the `hasChunksAt` guard (rare: chance-gated, once per 20 min); not wrapped.
- Release into chunks that are not FULL alone does not stall today's code on the perf worker (two diagnostic runs: 1.66 s, the hopper, and 0.83 s).
