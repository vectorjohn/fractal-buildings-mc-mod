## Round 5 (2026-10-27, lead-coder): stuck vs leak

- **Answer: neither. The server-form flight never loaded a chunk along its path.** Per-decision logging (`[LANE-START]`, every stubless decision with the nearest settlement) on beebox at e2a65c67: all 60 flight-and-settle decisions were the 12 start chunks around spawn (chunks -16..14, -15..15, at tick 0), 5 tiers each, all `no-owner`; 0 stubs, 0 builds, 0 biome rejections; nothing at the city. Cause: `MockPlayer` moved by `teleportTo` only. Vanilla moves a player's chunk view in `ServerGamePacketListenerImpl.handlePlayerPositionChange` (a client move packet; `ServerPlayer.tick` calls `ServerChunkCache.move` only while spectating another entity, javap 26.3), which a dead connection never reaches. So every server-form flight row so far (tick p95/max, lane counters, inline share) measured nothing but the warmer. Fix: `MockPlayer.flyTo` = `teleportTo` + `getChunkSource().move(p)`; the smoke game test checks the player's section follows (mutation: without the move it fails, "section x 0 at block x 3097").
- r4's "12 begun, 0 finished" was the peak of 12 concurrent decisions at spawn, read as stuck; the in-progress counter also leaked any stub never built (biome filter, and `StructureCheck` for /locate calls `findValidGenerationPoint` without building, javap). Fixed: LaneStats splits a start into decision and build; in-progress counts threads in either, so it cannot leak (`LaneStatsTest`, 4 cases; mutation fails 3). New counters: decisions, stubs, biome-rejected.
- Settle: the warmer's own task counted as pool activity (it was queued before its in-task counter), so quiet reset every second. Warms are now counted from submission; the settle is quiet when nothing but warms is queued or running, the last warm was under 1 s, no thread is in a start, and lookups/starts/postProcess are unchanged. At e2a65c67 it settled in 5 s (was 240 s).
- `perf.sh --world-mod-only`: only the mod world's server run, no planner, base, merge or check (diagnostics, about 4 min on beebox).
